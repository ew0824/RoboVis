📊 What the Profiler Measures

  • WebSocket Receive Rate: Actual Hz of messages received from backend
  • Visual Render Rate: Actual Hz of frames drawn by browser
  • Frame Processing Time: Time to process each WebSocket message
  • Frame Drops: Messages received but not rendered
  • Queue Backlog: Messages waiting to be processed
  • Long Tasks: JavaScript blocking browser rendering
  • Memory Usage: JavaScript heap size and GC pauses

🎯 Expected Results

Hypothesis: 90Hz backend → Laggy because frontend can't keep up

Scenario 1: Backend at 100Hz (laggy)

Expected Results: - WebSocket Rate: 100 Hz - Visual Rate: 30-50 Hz (can't keep up) - Processing Time: >20ms per frame (exceeds 60fps budget) - Frame Drops: High - Queue Size: Growing backlog Diagnosis: Frontend rendering bottleneck

Scenario 2: Backend at 50Hz (smooth)

Expected Results: - WebSocket Rate: 50 Hz - Visual Rate: 50 Hz (matches input) - Processing Time: <16ms per frame (within budget) - Frame Drops: Low - Queue Size: Stable Diagnosis: Frontend can handle this rate

🔧 Troubleshooting

Problem: "WebSocket not found" Solution: Make sure Viser is running and connected Problem: "No performance data" Solution: Wait longer, ensure robot replay is active Problem: "Profiler not starting" Solution: Check browser console for errors Problem: "Metrics display not showing" Solution: Check for ad blockers or CSP restrictions

📈 Performance Analysis

The profiler will automatically analyze the results and provide:
  • Rate Gap Analysis: Difference between data rate and visual rate
  • Bottleneck Identification: Whether issue is processing or rendering
  • Frame Budget Analysis: How much of 60fps budget is used
  • Optimization Recommendations: Specific suggestions for improvement
